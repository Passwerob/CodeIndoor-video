# High-School Bedroom Scene Planning Failure Analysis

## Conclusion

The problems occurred mainly at the scene-planning and shell-assembly interface, not from insufficient single-object aDSL modeling capability. The failures fall in two phases: early on, the open-ended requirement led the design stage to associate a "high-school bedroom" with objects the user did not ask for; later, after the user gave a closed-set object list, the list was preserved correctly, and the failures concentrated on the room shell's wall segmentation, door/window openings, support relations and coordinate baseline.

The more worthwhile system problem to fix is: FineScene can recover the same frozen plan within the current run, but does not proactively retrieve similar shell recipes that have already passed validation in other runs. Such existing successful results do exist.

## Run Evidence

- `high_school_tatami_bedroom_agent_20261028_11` used an explicit list: desk, chair, tatami, window, bed, cabinet; a desk lamp and a few books on the desk; and explicitly excluded laundry basket, plants, rug, side table and ornaments. Its final decomposition list did not add these extra objects. So complaints such as "laundry basket" correspond to the earlier open-ended attempts, not to the result of this strict list.
- Run 11 made 16 model calls, about 409,131 tokens and 741 seconds of cumulative call time. The first shell-recipe round took about 76 seconds. Several kinds of rework also occurred before reaching the shell: a missing content label in a request, a window wrongly given a shell-child origin relation, a visual partition encoded as a 0.5 m hard gap between the bed and the tatami, and a shell bounding box failing ground contact.
- Run 11's `architecture_backend_arch_shell.json` shows that the dedicated shell backend was incompatible: the planner froze several wall-segment IDs such as `wall_rear_left/right/header/below` and `wall_front_left/right/header`. The dedicated compiler needs one whole-wall ID per side and cuts the wall automatically according to the openings. The compatibility gate therefore sent the request to the generic recipe model, asking it to rebuild all wall segments, door frames, openings, connection relations and parameter expressions in one go.
- Run 11's stage metric is 6 of 12 first-round candidates passing (50%); this is a "stage first-round pass rate", not a "whole-scene one-shot pass rate". The failed stages include decomposition, functional binding, spatial plan, layout and shell recipe.
- The resumed run 12 made another 5 model calls on the shell, 185,336 tokens, about 468 seconds, and still did not pass. The logs show the errors changing back and forth among wall-panel orientation ratio, header connection, support target, door/window opening intersection and the 0.05 m floor slab versus the world ground baseline; the resume did not converge to a valid shell.
- The earlier local `high_school_tatami_bedroom_agent_20261028_10` has a validated shell recipe: the frozen room is likewise 4.2×4.2×2.8 m, and its first shell-recipe candidate passed, taking about 45 seconds. It used segmented walls and the generic recipe path, proving that this wall-and-opening topology has been built successfully before.
- That successful recipe cannot be copied as-is to runs 11/12: the old run's doorway is on `x_min`, 0.98 m wide, with a window opening 1.70 m wide and sill height 0.85 m; the new run's doorway is on `y_min`, 0.90 m wide, with a window opening 1.10 m wide and sill height 1.40 m. The old run treated the entry door as an independent child component of the shell, while the new run froze the leaf, frame and handle inside the shell. The right approach is to treat the old recipe as a validated structural template, rebind IDs, openings and local coordinates, and hand it to the existing validator for re-check, rather than copying the final geometry unchecked.

## Why There Was No Reference

The existing recipe-reuse path mainly covers explicit recovery of "the same frozen plan": object IDs, requirements, spatial contract and layout must all be identical, after which the earlier recipe is handed to the current validator for re-check. Runs 11/12 differ from run 10 in plan IDs, door/window positions and door-component ownership, so this strict reuse path does not automatically pick up run 10's recipe. What the system lacks is a cross-run step of similar-solution retrieval, difference mapping and candidate validation.

In addition, the `system_source` packaged with runs 11/12 still contains only the generic note "use non-overlapping wall panels around openings", without the current dedicated mapping contract. The current contract allows a frozen ID to represent a whole wall, and also allows splitting by the actual door/window openings into piers, below-sill and lintel units, and so on; the compiler computes their sizes from the accepted spatial openings. It is compatible with run 10's segmented-wall approach and does not require turning each wall into a single ID. These changes came after runs 11/12, and cannot be read backwards as the old runs already having used the new backend.

## Parts of Existing Research Worth Borrowing

- The public object-selection prompt of Holodeck (CVPR 2024) requires at least 10 categories of large objects and pursues livelier, richer rooms. This is opposite to the lean object list explicitly given by this user, and its object-count target should not be copied. What can be borrowed is splitting object selection and spatial layout into explicit stages; its public prompt itself cannot solve this project's wall-assembly contract.
- The prompt template of HDSL (2026 preprint) stipulates that each round generates only the direct children of the current-level node; when crowded or overlapping, optional large objects are deleted; and compact bedrooms have dedicated trimming rules. The portable principles are keeping the room list a closed set, stating the scope of hierarchical planning clearly, and having failure feedback change only the local objects or relations that caused the error. HDSL uses its own hierarchical DSL and validation flow, and its full prompt cannot be taken directly as an executable FineScene prompt.
- Public material (locally saved web copies are not checked in): [Holodeck, CVPR 2024](https://arxiv.org/html/2312.09067v2); [HDSL, arXiv 2026](https://arxiv.org/html/2606.09738v1).

## Current Fix and Boundaries

The source has extended the deterministic shell compiler so that it can map the wall IDs frozen by the planner, according to the real openings, to whole walls, left/right piers, below-sill and above-opening units; the compiler computes all sizes directly from the spatial openings, so the model does not have to guess wall-block coordinates again. The compiler also supports connecting the separately frozen door-frame left/right jambs and door head in the plan to the corresponding generated components, while retaining the original full geometry/assembly/opening validation. A wall header is counted into the wall-grid capacity as a beam form, and is not confused with the door head in a door frame.

At the same time, the decomposition prompt states explicitly that a lintel is a beam along the wall direction and cannot be supported by the floor; decomposition validation rejects such impossible interfaces before the expensive recipe construction. The closed-set object list and floor-slab height constraint are also made explicit. The offline replay copies run 11's frozen plan into memory, corrects only the two lintel support/form errors confirmed by the evidence, and then uses the deterministic compiler to compute the wall grid; all 16 components pass the current geometry, assembly and door/window opening checks. The script `experiments/diagnose_bedroom_shell_replay.py` does not call the model and does not change old run files. The full experiment regression now stands at 493 passed; the shell replay passes and the syntax check passes. Of the 5 tests that initially failed, 4 were compatibility checks that assumed the test object must have an optional semantic field, now changed to a safe default; the other test mistook an automatically copied frozen rigidity for an error needing model rework, and now checks the result of the automatic lowering instead.

## How to Raise the End-to-End First-Round Success Rate

Prefer turning deterministically computable constraints into program behavior, and leave the model for real decisions. The object list given by the user should stay closed in the request contract and scene design; the spatial stage selects only positions, orientations, circulation and openings; the shell compiler computes wall segments, lintels, sills and seams from the accepted door/window contract. This way the model does not have to reinvent wall-segment coordinates, sizes and connections. Rather than copying run 10 as-is to run 11, it is more reliable to borrow its validated segmented topology, have the new compiler regenerate it according to run 11's door/window positions, sizes and IDs, and then pass it through the current validator.

Each round of evaluation must look at "number of scenes whose initial candidate fully passes system acceptance / number of fully generated scenes", and separately record each stage's initial pass rate, repair calls, tokens, time and final Judge results. Run 11's 6/12 only shows that some stages need optimization and cannot replace the end-to-end rate; run 10 has a different prompt, openings and room objects, and cannot be used as a control under the same conditions. The current offline replay proves that the known defect of the shell interface can be eliminated by a deterministic implementation, but furniture layout, rendering or end-to-end one-shot passing has not yet been verified. The next full run should be treated as a costly acceptance trial: first check the new stage statistics and output evidence, then decide whether to continue changing model prompts or whether the model needs adjusting.
