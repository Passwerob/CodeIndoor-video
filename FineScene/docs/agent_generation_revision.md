# General Agent Generation Revision (2026-10-20)

## Working boundary

The system developer modifies the planning protocol, expressive power, compiler, validators and feedback flow; the actual object list, dimensions, layout and repair values are generated by the agent.
The visual Judge, service-failure retry, repair work orders, repair candidates, re-rendering and final acceptance must all be executed by the agent main loop through the normal entry. The developer inspects code and run records, does not replace the system Judge with their own opinion from looking at images, and does not manually invoke a single repair round outside the entry to claim an autonomous closed loop.
`experiments/build_flash_bookshelf.py` is a previously hand-orchestrated diagnostic sample and **must not be used as evidence of general agent generation success**.
Later verification uses `src/run_general_scene.py` with natural-language input. A replay must explicitly record the source plan.

## Mechanisms of this round

1. **Original requirement contract.** Independently extract the single-asset/scene boundary, quality goals and explicit quantity ranges. The decomposition must conform to the boundary, and repeated content is labeled with a requirement tag per instance. One asset must not be split into dozens of scene objects while claiming to satisfy the requirement, nor may a quantity in the description stand in for actual instances.
2. **Batched assembly.** A large parametric asset first generates the structure and interfaces, then content parts in batches of at most eight according to support dependency. Each batch's model reads the dimensions, centers and bounding boxes of the already-compiled geometry; the structure is not filled with coordinates by the program, all of it comes from the model. Later batches cannot rewrite parts that have already passed. The final merge must still pass the complete assembly and edit checks.
3. **Executable physical feedback.** Assembly-failure feedback includes measured interfaces and distinguishes top-surface support, side fastening and bottom-surface fastening. A joint verification between a cylinder's flat end face and a box's flat face is added; side contact on a curved surface still cannot be proven by a bounding box. Support, clearance and rigidity constraints are kept.
   For internal contents whose support relation the model has declared and whose initial contact has been verified, but which still use absolute constant coordinates, the compiler converts them into poses relative to the support surface. The per-part bounding boxes must be identical before and after conversion; it must not mask the original floating/interpenetration through automatic snapping. This rule applies to supported contents of any category, and explicit expressions remain under the model's control and subject to edit checks. The original model output is kept, and the final executable plan contains the converted parent/mount.
4. **Component and material capabilities.** A reusable book sub-assembly can be used in any scene, keeping the cover, page block, spine and different bindings; it is not a complete bookcase template. The general material catalog provides verified local PBR resources, and surface parameters include texture resource ID, texture direction, scale and roughness. The model can choose among these capabilities.
5. **Visual repair has real controls.** Material work orders can modify finish/surface/color and re-render for review; color is no longer the only control. Geometry work orders cannot pass by shrinking rigid objects, deleting relations or lowering quality requirements.
6. **Real runs and reproducibility.** Planning/Judge default to `deepseek-flash`. The official current mapping is DeepSeek-V4.1-Flash-1017; planning uses the documented low reasoning effort, with a 32,768 total output budget that accommodates reasoning and the full JSON. The cache also contains the model-profile file hash; new CLI runs save a system source snapshot and the entry provenance. A failed stage with the same input can also be resumed: it is first re-validated with the current validators, then the model repairs it precisely; stages that already passed need not be redone.
7. **Diagnostics and Judge protocol.** Reference errors list the actual illegal IDs and the legal scene-object IDs; the decomposition stage supports JSON-pointer repair down to leaf fields. The Judge's passed/needs_revision must be consistent with the blocking findings; on a contradiction the model re-reviews the same images once, and the program does not take it upon itself to change the result to passed. The static appearance review and the parameter-edit measurement each bear their own evidence responsibility.

8. **In-system visual closed loop.** For small scenes, up to six views are judged together; for large scenes, a local batch includes a panorama from the opposite direction, reducing false reports from occlusion. When the vision service is unavailable, the system automatically retries once with the same set of images and keeps the records separately; a visual failure is not retried as a network error. A camera work order can have the repair model modify the viewing azimuth, after which the normal flow re-renders and re-judges; a framing problem cannot be satisfied by changing the geometry. The repair model receives the last rejected candidate and the error attribution, to avoid attributing errors introduced by a candidate to the original asset.

## Problems revealed by failures

- The default high reasoning mode once used up 16,000 output tokens without producing JSON; turning reasoning off in turn produced clear errors in source and assembly reasoning. Low reasoning effort still needs to reserve a sufficient total budget for the final structured output.
- The model once split a single bookcase into a cabinet plus dozens of scene-level book objects, which prompt text alone could not prevent. The requirement contract validates this explicitly.
- The model once understood `auto` as automatically generating aDSL. The interface and error feedback now state explicitly: auto means retrieving/generating an external mesh; editable internal_parts must use parametric.
- The model once wrote the thickness of a horizontally stacked book as 0.37 m; the geometry check intercepted the penetration through the shelf board. That manual diagnostic sample does not count toward the agent success rate.

## Baroque prompt trial and loop correction

The user asked to try a Baroque bookshelf with richly varied, staggered book arrangement. The original prompt is saved in `runs/agent_baroque_bookshelf_20261020_01/run_origin.json`, and the later `_02` and `_03` normal-entry runs used the same prompt and the stage checkpoints. The shapes, parts, coordinates and repair values all came from the model; no Baroque scene constructor was hand-written.

This exposed and corrected two general problems:

1. Previously the two repairs per stage would stop too early when different validation errors were exposed one after another. The default planning limit is changed to six, configurable with `--max-planning-repairs`; on a repeated identical candidate with identical errors it stops early and records `repeated_failed_state` or `repair_budget_exhausted`. This is only bounded progress and loop detection, and it cannot be claimed that automatic cross-stage re-planning is supported. In the real run, the content batch finished the support check only after the third repair.
2. Checking only whether a parameter name is referenced cannot prove an edit is effective. The model once output a zero-valued expression in which parameters cancel to get around the unused-parameter check. `edit_general` now compares the measured part geometry and the scene bounding box before and after the edit, and edits with completely no change are rejected. A single-asset recipe stage checks the actual effect right there; in a multi-component plan a local recipe is allowed to be unaffected by the edits of other components, while the complete plan must still have an effective change. This item proves a non-empty edit effect, which is not equivalent to fully verifying every edit semantic in the natural language.

The regression tests this round total 70 passed, including resolving three different errors in succession, early stop on a repeated failed state, and rejecting invalid edits caused by cancelling parameters. `_02` is a candidate produced by the old edit validator and can only be used to show the shape at that time; its pass record cannot be used to claim that the level-spacing edit is effective; `_03` re-checked and repaired the structure and content recipes with the corrected validator.

The actual `_03` recipe has 28 detailed book sub-assemblies and 17 box parts. Its first-round system Judge found that the staggered arrangement and whitespace basically held, but that the Baroque curves, scroll feet and carved crown were not implemented, and judged `needs_revision`. This reveals a shortfall in the current decorative geometry expression and acquisition strategy: the appearance of style text in the plan does not prove that a corresponding curve or carving implementation exists. This trial cannot be taken as evidence of Baroque style generation success.

`_03` has finally ended: the main loop proposed two local repairs, both intercepted by geometry/edit validation, and no valid candidate that could enter the next round of rendering was produced; the first-round rendered result is kept, and the final `run_report.json` is `rejected`. This round is therefore one round of rendering/visual review plus two failed repair proposals, and cannot be counted as three rounds of visual review. The final display files are `_03/visual_review/overview.png` and `front.png`, and the editable Blender file is `_03/visual_review/review.blend`.

## Style must be realized in geometry (later revision)

Added `src/style_contract.py`. In the request-extraction stage the model breaks an explicit style into visual features and evidence requirements, distinguishing regular solids, complex surfaces and surface effects. The decomposition must bind each requirement to an actual component. Since the existing aDSL recipe has only box/cylinder/sphere/book, a complex-surface requirement must be bound to at least one retrieve/auto/generate sub-asset; a carving name or an unimplemented sweep capability cannot pass for geometry. A single asset keeps one parametric root, and the other external shapes are replaceable rigid descendants; the whole asset is not replaced by an uneditable mesh.

Style requirements and bindings enter the final plan, and local repair cannot rewrite them. The visual Judge returns per-item `style_assessments` and visible evidence; protocol contradictions such as a missing item, missing/unclear yet passed, or a missing associated blocking item trigger a model re-review, and the program cannot let it through on its own. Local component views review only the relevant style entries, while the panorama still reviews all entries. This protocol constrains the completeness of review, and does not guarantee that the model's visual judgment is always correct.

The normal entry gains `--max-replans` (default one): after a local repair has no valid candidate, a structure/source-type visual problem, or an asset-acquisition failure, the system can re-decompose and acquire assets again. The original request contract, style and quality stay frozen, sharing an asset cache with acceptance and hash validation; each round saves its own `attempt_report.json`, and the root directory records `generation_rounds.json`. This is a bounded whole-round fallback, and there is currently no fine-grained incremental scheduling across stage dependencies.

The real run `runs/agent_baroque_style_contract_20261020_01/` produced one aDSL root and six external decorative sub-asset routes (curved side ornament, scroll crown ornament, carved panel, cornice, base). In the end none of the six was accepted and all were rejected before program integration; there is no new qualified bookshelf, and no evidence of a TRELLIS success. The candidate ordinary furniture was rejected visually, and an overly long reference query found no images. The initial whole-round fallback of that run was triggered by `APIConnectionError`, and cannot be recorded as evidence of a visual/style-driven fallback; it has since been fixed: a temporary service failure is retried on the same request, and after exhaustion no design re-planning is performed. Visual-driven fallback is currently covered by mock regression, and still awaits an end-to-end run with actual qualified assets.

Asset acquisition adds that the agent rewrites the description into at most three short image-library search terms, saving `reference_search.json` and the model-call record; a single download failure does not discard the other candidates of the same batch, and a reference image must still pass visual QA before TRELLIS.1 is called. Retrieval results are no guarantee of usable input.

The latest tests total 78 passed, newly covering: style cannot be satisfied by renaming boxes, style entries cannot be lost, the whole editable asset cannot be replaced by a mesh, vision must review item by item, the normal entry keeps the contract through automatic fallback, service failures do not fall back the design, and search-term correction and local download-failure isolation. The tests do not prove that the Baroque shape has succeeded.

Later tests grew to 79; the fallback context newly includes the actual failure constraints and a source summary of the previous decomposition; asset failures are returned in a structured reason, not just a file path. `agent_baroque_style_contract_20261020_02` actually intercepted the scheme "a complex style still bound to an ordinary parametric root", and after automatic re-decomposition produced an independent carved sub-asset. The new query flow raised the crown-ornament reference search from 0 to 6 image candidates, but all six reference Judge runs were unavailable due to output-protocol contradictions, and cannot be recorded as visually negative candidates; TRELLIS was not started. The developer interrupted the run that kept consuming candidates and recorded `developer_interruption.json`, adding a raw Judge decision log and a precise re-review prompt. The explicit replay mode of the normal CLI was then used to run `agent_baroque_style_replay_20261020_01`; what it replayed was the plan the system had already generated, with no asset values changed by hand. The current entry falls back/ends once the acquisition of the first required asset is exhausted, and records the components that were not executed, to avoid continuing to consume sibling assets that cannot be assembled.

That replay has ended and was rejected: neither the 3D candidate for the first required crown ornament nor the six reference candidates were accepted, TRELLIS was not called, and the remaining nine components are listed in `pending_components`. The raw Judge responses confirmed that the earlier contradiction came from component/reference reviews without global style entries still filling in style_assessments themselves; after the precise re-review prompt a valid rejection verdict could be returned. External references still need expanded sources or a reference-generation capability, and it cannot be claimed on this basis that Baroque asset generation has succeeded.

## 2026-10-25 update: spatial diagnostics and continuous repair

Spatial design validation now merges independent errors such as composition relations, room boundaries, entrance/passage and edit-dimension capacity, and hands them to the Agent for a single repair; when one class of check reports an error, the remaining runnable checks are not skipped. Planning stages, layout/spatial re-planning, whole-scene visual repair and whole-round source/structure re-planning no longer use a fixed round cap. They stop on pass, service unavailability, or repetition of the same candidate with the same failure evidence; every candidate must still re-run the full validation, and visual repair must still be re-compiled, rendered and pass the independent Judge.

The regression tests cover cross-validator aggregation of composition and zone errors, and continuing to handle different visual problems under the old `max_repairs=0` parameter. The current complete usable test suite has 271 passed. The TRELLIS texture-export test was not executed because `trimesh` is not installed in the run environment.

Run 38 hit a `RemoteProtocolError` in the spatial-planning stage and produced no final Blender scene. The coarse layout solve of Run 40 passed; Run 42 continued generating components from the re-validated plan and layout, the room structure passed after two repair rounds and the fireplace after one. These local checks, bounding-box previews or layout solves still cannot be recorded as the success of a complete scene.

This round continued to fix mechanism differences between the solver and the acceptor: the planar position of a supported child object can be solved independently; the normal coordinate of the semantic access side is consistent between the two; the coarse layout validates the access zone against the actually rotated declared envelope, while the measured-geometry audit still uses measurement evidence; the joint passage output compresses degenerate turning points; the mounting orientation comes from the contact face chosen by the Agent. After spatial re-planning, the system first fully re-checks the old Agent layout, and only if it still does not hold calls the layout model again, passing in the latest complete failure diagnostics. All changes apply to the general geometry and planning flow, with no hand re-arrangement of any particular room.

Access planning now reads the complete active group; for related access conflicts it allows re-auditing the conjectured entry side and along-face offset, and the validator forbids shrinking the access zone, lowering the passage width or losing functional objects. The structured room backend adds a binding-capacity check, and multiple independent wall structural parts now go through the general aDSL recipe, avoiding repeated patching in a mode that lacks the expressive power. Geometry recipes use low-effort reasoning and receive local bounding boxes computed from verified root poses and the local height of the world ground; these are only coordinate-transform evidence, and not the program designing parts for the Agent.

The repair input keeps all problems, measurements and frozen constraints, reducing duplicate expansion of diagnostic copies and writable pointers. The same 321 problems and 23 part measurements of Run 41 were reduced from 462249 characters to 190105 characters in compact JSON, with all source problem IDs still present. The rejected patch state and the actual assembly findings continue to be passed in, to avoid losing physical evidence in order to shorten the context.
