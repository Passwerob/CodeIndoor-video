## 1. Mapping principles (the fundamental difference from v1)

| | v1 (implied by the audit version) | **v2 (finalized by the user)** |
|---|---|---|
| Verbs | translate / convert / take over | **take over / wrap / index** |
| Who changes | Implied that SceneCode must cooperate by outputting structured data | **Only aDSL changes** |
| Upstream artifacts | Treated as intermediate formats to be normalized | Treated as **immutable input facts** |
| ID | aDSL generates its own set of IDs | **Directly adopt `PartPlan.name`** |
| Program | Expected to be changed into structured parameters | **Take over the `.py` as-is, adding a contract around it** |

In one sentence: **do not require SceneCode to become more like aDSL; let aDSL accommodate SceneCode as it is.**

## 3. `ProgramComponent` contract (P1, to be implemented)

**The task explicitly forbids**: "do not simply stuff an arbitrary Blender Python string into a JSON field and then claim aDSL is implemented".

So `ProgramComponent` is not "a string holding code", but a **compilable component with semantics, parameters, a coordinate frame, dependencies and validation**:

```python
@dataclass
class ProgramComponent:
    component_id: str            # = SceneCode PartPlan.name, stable, immutable
    source_path: Path            # upstream code/<part>.py, read-only reference
    source_sha256: str           # program version fingerprint, used for dirty detection in incremental execution
    entrypoint: str              # build function name per SceneCode convention, e.g. create_backrest()
    params: Dict[str, ParamSpec] # structured parameter table (name/type/unit/range/default)
    local_origin: Vec3           # local origin (derived from world coordinates, done on the aDSL side)
    local_frame: Mat4            # local coordinate frame 4x4
    output_aabb: AABB            # bounding box measured after execution, for the relations solver
    depends_on: Tuple[str, ...]  # other component_ids it depends on
    upstream_refs: Dict[str, Path]  # original paths of ObjectPlan / pipeline_result / render
    revisions: List[ActionTrace] # SceneCode's repair history
```

Key constraints:
- `params` is a **structured parameter table**, not a free dict. `Test A` (chair back −5cm) and `Test C` (armrest +3cm and left-right symmetric) must be achievable by changing named parameters, not by regenerating the whole code.
- `source_path` is a **reference**, not code moved into JSON. What the aDSL AST stores is "which program + what parameters + what coordinate frame + depends on whom".
- `compile()` produces a Blender Python execution fragment and `execute()` hands it to the incremental executor; the two are separate.
- If the upstream-generated `.py` cannot satisfy the `entrypoint` / `params` contract, the ingester **raises an explicit error and lists the missing items**, without silently downgrading to a few cubes.

### 3.1 Can the code generated by SceneCode be wrapped?

**It cannot be wrapped automatically as-is, but SceneCode does not need to change.**

The audit confirmed that the part-wise code is arbitrary `bpy` strings freely generated by the LLM, and `PartShape` is only a prompt input. The remedy sits on the **ingestion side + prompt side**, both in the aDSL/bridge layer:

1. The aDSL ingester performs static analysis (AST) on each `<part>.py`, extracting the top-level `create_*()` function, literal constants and size-related expressions → producing `ParamSpec` candidates.
2. Parameters that cannot be extracted statically are marked `opaque`, and it is **explicitly recorded that this component does not support parameter-level editing** (Test A/C can only pick parameterizable components, which is honestly noted in the acceptance).
3. Through the gateway, **append a contract note to the Planner/Constructor prompt** (without changing the SceneCode source, only supplementing the system prompt injected by the gateway), guiding the LLM-generated program to expose a stable `create_<part>(params)` signature and named size constants. This is "the adaptation layer adapts to upstream" rather than "modifying upstream".

## 4. Stable ID rule (implemented)

```
component_id := PartPlan.name                    # preferred, already present upstream
             := stem(code/<part>.py)            # fallback
             := key of attach_part               # for pure aDSL construction
```

- **No UUIDs, no prefixes, no renaming**, so that aDSL and `house_state.json` / the `code/` directory can index each other.
- `Asset.attach_part()` binds automatically; `Asset.copy()` preserves it; `asset_to_dict/asset_from_dict` preserve it in round trip.
- Duplicate IDs raise an error at `component_ids()` (the incremental executor uses the ID as the Blender object key and must not silently overwrite).
- When an old JSON has no `component_id`, it is derived from the label, so that historical `outputs/*.json` can still be loaded.

Verified: `SceneCode_audit/tests/test_adsl_stable_ids.py` 10 items + the existing 14-item regression all green.

## 5. Spatial relation mapping (Test B )

SceneCode's `PartRelation` is commented out in `from_dict()` (`object_plan.py:221-222`), so **there is no usable relation data upstream**. aDSL cannot assume it exists based on the paper.

Where Test B "keep the coffee table and sofa center-aligned while ensuring a reasonable usage distance" lands:

| Requirement | aDSL mechanism | Note |
|---|---|---|
| Center alignment | `align_centers` (`layout.py:326`, note the plural), `align_anchors` (`:92`) | Modify the **relation constraints**, not the absolute coordinates directly |
| Usage distance | `RelationAssembly.bound/within/supported` (`relations.py:83/128/120`) | Expressed as a parametric distance constraint, recomputed by the solver |
| Do not blindly change all coordinates | `Expr` / `parameter` / `datum` (`relations.py:23/71/77`) | Re-solve only the affected objects |
| Local re-solving | **P4 to be implemented** | `RelationAssembly.compile()` currently always returns a brand-new scene (comment at `:61`); it must support local re-solving by stable ID |

## 6. Missing aDSL operations and the minimal extension list

| Gap | Can existing capabilities express it? | Minimal extension | How to verify |
|---|---|---|---|
| Take over arbitrary part-wise programs | ❌ No corresponding type | `ProgramComponent` (§3) | Ingest a real `<part>.py`, and be able to compile and execute it to the same geometry |
| Component-level parameter editing | 🟡 `Expr`/`parameter` provide a basis, but cannot bind to programs | `ParamSpec` + `bindings` | Test A / Test C |
| Stable ID | ✅ **Completed this round** | — | Round trip + copy + old-JSON tests |
| Two-way serialization | ✅ **Completed this round** (core library `asset_from_dict`) | — | Same as above |
| Dependency graph / dirty marking | ❌ None | `DependencyGraph`, based on `component_path()` | After editing a single component, the dirty set == the expected closure |
| Incremental Blender execution | ❌ `clear_scene=True` full rebuild | Delete and rebuild a subtree by `component_id`, other `bpy` objects keep their handles | "Non-target geometry is not regenerated" in Test A/B/C |
| Local relation re-solving | ❌ compile always returns a new scene | `compile(changed_ids=...)` | Test B |
| aDSL ↔ Registry ↔ Blender consistency | ❌ No check | Three-way diff keyed by `component_id` | State Consistency in the acceptance table |
| CSG | ✅ `boolean.py` already exists | No extension needed; but SceneCode has no CSG, so it must not be mapped from nothing | — |
| ExternalMesh | ✅ Already exists | Used only as a reference to existing assets, not promoted to a primary geometry method | — |

**Extension discipline**: each extension must state its semantics, parameters, inputs/outputs and verification method (required by the task's PHASE 4). The table above is the initial list, and specs will be filled in item by item during implementation.

## 7. Things explicitly not done

- ❌ Do not turn SceneCode's `ObjectPlan` into a synonym of the aDSL AST (the task text already warns "do not assume ObjectPlan is equivalent to aDSL").
- ❌ Do not downgrade complex objects to a few Cube/Sphere/Cylinder.
- ❌ Do not merge all parts into a single uneditable Mesh.
- ❌ Do not lose articulated capability by introducing aDSL (the `Joint` tree can already take it over).
- ❌ Do not let a localized edit regenerate the whole room (this is exactly what P3 must solve).
- ❌ Do not stuff an arbitrary Blender Python string into a JSON field and call it "aDSL implemented".
- ❌ Do not modify SceneCode business source to satisfy any of the above.
