## 1. Question: why is our single-object aDSL generation so bad?

**Answer: aDSL single-asset generation is not bad at all; I simply did not use it, and instead went around it to start my own scheme of having the LLM write raw `bpy` code.**

aDSL already contains high-quality single assets, built in a way completely different from mine:

- `E:/3DUse/aDSL/outputs/medieval_armchair_20261017/model.py` — "Oakwarden": `gothic_arc(side, steps=28)` samples a cubic Bézier into `Cylinder` segments, `ellipsoid()` is obtained from `scale_shape(Sphere(1), ...)`, mirror symmetry, 17/15/12 sets of brass studs, with an attached `PLAN` contract (parts / relations / build_order / checks).
- `present.py` in the same directory — Blender surface refinement: cushion, swept trim, piping, materials. Produces `review_02/medieval_armchair.blend` + `.glb` + `hero/front/rear.png`.
- `E:/3DUse/aDSL/examples/physical_bookshelf/model.py` + `book_library.py` — `RelationAssembly`'s `parameter/datum/span_box/box/attached/rigid/supported/within`, deterministic `random.Random(20261017)`, each book composed of cover / aged_pages / spine / binding_band / gilt_rule / spine_label / page_edge.
- aDSL core itself provides `RoundedCube`, `boolean_union/difference/intersection`, `attach_part`, `RelationAssembly` — fine geometry relies on **parametric functions + composition + relation constraints**, not on the LLM imagining bpy calls.

**The most damning counter-evidence**: the file title of `E:/3DUse/aDSL/create_laptop_fixed.py` is literally "fix the code generated by DeepSeek to match the aDSL API", and in `E:/3DUse/aDSL/generate_with_deepseek.py` the model is told to "return Python code only". In other words, **the fact that "having DeepSeek generate raw aDSL/bpy code requires manual fixing" had already been hit and recorded in this project long ago**. I did not read those files and stepped on the same trap again.

## 2. Question: why are FineScene single-object generations good?

**Answer: FineScene does not let the LLM write geometry code at all.** The LLM only outputs a **structured JSON plan** strongly validated by pydantic `StrictModel`, and the geometry is produced by a deterministic compiler.

The official pipeline at `E:/3DUse/FineScene/README.md:5`:
`LLM Planner → Constraint Solver → aDSL Builder → Asset Assembly → Geometry Judge → Render → Vision Judge`

Key implementation:

| Mechanism | Actual location |
|---|---|
| Parametric factory library; the LLM only fills in parameters | `FineScene/src/adsl_components.py:388` `FACTORIES = {bookshelf, shelf, desk, chair}`; `:396 build_component()` filters LLM parameters with `inspect.signature(factory).parameters` (`:414-415`), and the details are generated deterministically by code |
| Directly reuses aDSL core | `adsl_components.py:10` `from adsl.core import Asset, Cube, Cylinder, ExternalMesh, RelationAssembly, shape_aabb, ...` |
| Geometric constraints + measurement | `constraint_solver.py::judge_component_bounds`, `edit_judge.py::judge_edit`; `finalize_scene.py` reads the actual AABB from Blender and writes `blender_world_bounds.json` |
| Existing high-fidelity assets first | `asset_registry.py::resolve_local_assets` (reuses `medieval_armchair.blend`); `assemble_refined_asset.py::append_blend_asset` uses `bpy.data.libraries.load` to keep the full material nodes |
| Retrieval fallback | `general_assets.py::local_catalog / search_polyhaven / ...`; in `auto` mode TRELLIS.1 is called only when retrieval fails |
| Engineered materials/rendering | `realistic_refiner.py::surface` (PBR diffuse/roughness/normal/ARM), Cycles + AgX + HDRI |
| Editability | Stable IDs + deterministic seeds + parameter propagation; an edit recomputes only the affected closure |

**No component path where an "LLM generates a Blender Python string" was found anywhere in the FineScene repository**; every `import bpy` lives in a fixed worker script.

## 3. Question: how did it pass the visual review?

**Answer: because I made the Critic an "onlooker that scores after assembly" rather than a "per-object release gate". This is my system design error.**

| | FineScene | My setup |
|---|---|---|
| Timing | **Per candidate, object by object**, before assembly | Evaluated once, after everything is assembled and rendered |
| Evidence | Per-object three views front/rear/side + SHA-256, `general_assets.py:997 prepare_candidate` → `review_images(..., scope='component')` writes `visual_qa.json` | Only 3 whole-scene viewpoints |
| Does it block | **Yes**: `:1050 record['accepted'] = verdict['accepted']`, `:1075 if record.get('accepted') is not True` directly rejects it; reference images are also judged one by one (`:1229-1235`), and a service failure / insufficient evidence does not pass | **No**: `visual_critic()` only returns `score/issues` that go into the report; no branch stops the artifact |
| After a failure | `execute_with_repairs` keeps repairing and re-rendering, with up to 3 LLM re-plans | Records one issue line and delivers as usual |
| Per-object execution checks | Component AABB, rigidity, stable IDs, source-consistency recheck | `part_runner.py` only verifies "has a `build_part` function + has mesh vertices" |

So in `part_runner.py`, an armrest program that produced a 2.5 m elliptical disc gets `ok=True` as long as it returns an object with vertices; even if the Critic later gives it 3 points, that only leaves one `issues` line in the JSON, and **no code path rejects it**. That is "how it passed": it simply has no gate.

## 4. Root-cause summary

It is not that "DeepSeek is not strong enough"; it is that **I put the generative model at the wrong abstraction layer**:

1. Having the LLM directly produce `bpy` code strings → no schema, no size constraints, no part semantics, not reproducible, no local repair; the project already has `create_laptop_fixed.py` proving that this route needs manual fixing.
2. I built my own `ProgramComponent` + sandbox, yet **did not reuse** the `FACTORIES`, `RelationAssembly`, `append_blend_asset`, and high-quality asset library that FineScene/aDSL already have.
3. Quality checking was made an after-the-fact onlooker scoring rather than a per-object hard gate; so any junk geometry could run through the whole chain and be taken by me as "works end to end".
4. Worse, I used "15/15 passed" as the success metric — that "pass" only means "no exception was thrown", not "does it look like a sofa".

## 5. The right approach (next steps, redo following FineScene's way)

In priority order, and **without adding new abstractions on my own initiative**:

1. **Stop the path where the LLM writes raw bpy for part generation**, and mark `agentic_coder.py` as deprecated (keep the run results as evidence, no longer as a system path).
2. **The LLM outputs only structured plans**: reuse FineScene's `SourceDecision / PartSpec / ComponentPlan` (pydantic strongly validated) or SceneCode's `ObjectPlan`; the model is responsible only for "part kind + parameters + semantics" and produces no geometry code.
3. **Geometry is compiled by deterministic aDSL factories**: reuse `FineScene/src/adsl_components.py::build_component` / `FACTORIES` and aDSL core's `attach_part`, `RelationAssembly`, `RoundedCube`, CSG; if a sofa factory is needed, extend it in the style of the existing chair/bookshelf factories, rather than having the LLM improvise.
4. **Existing high-fidelity assets first**: reuse the `asset_registry` / `append_blend_asset` path (`medieval_armchair.blend` etc.), keeping the full material nodes.
5. **Per-object visual QA hard gate**: bring in the `general_assets.py::prepare_candidate` pattern — per-object three views + `scope='component'` Judge + release only when `accepted is True`; on failure, re-plan/re-retrieve, and never enter assembly. The whole-scene Judge acts as the second gate.
6. **Delete metrics like "15/15 passed = success"**, and instead use the Critic score + per-object accepted + measured geometric AABB together as acceptance.

**The aDSL representation does not need to change** — it was right all along; I just did not use it correctly. The user said this from the very start, and I took a long detour before confirming it.
